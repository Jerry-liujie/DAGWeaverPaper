\section{Introduction}\label{sec:intro}

\introhead{Trend}
Modern analytics is shifting from human-written, isolated SQL queries to large, continuously maintained SQL programs. Data teams are asked to serve more stakeholders, combine more sources, support AI-facing datasets, and expose governed data products faster; at the same time, BI tools, analytics engineering frameworks, and code-generation assistants increasingly generate or maintain SQL on behalf of users. dbt Labs reports that 70\% of analytics professionals already use AI for code development, 57\% still spend most workdays maintaining or organizing datasets, and nearly 65\% believe enabling nontechnical users to create transformed and governed datasets would improve organizational efficiency~\cite{dbt2025state}. The consequence is an efficiency gap: organizations and automated tools produce increasingly large, repetitive, and semantically rich SQL pipelines, while database optimizers still see mostly one submitted statement at a time.

\introhead{Query rewriting}
Query rewriting has become an important way to close this gap. Rule-based, synthesis-based, and LLM-assisted rewriters such as \emph{SlabCity}~\cite{slabcity}, \emph{GenRewrite}~\cite{genrewrite}, \emph{WeTune}~\cite{wetune}, and \emph{R-Bot}~\cite{rbot} improve SQL before it reaches the database optimizer. However, these systems inherit the same unit of optimization as the optimizer: one query. They cannot generally ask why a relation is being computed, which later outputs depend on it, whether sibling computations are semantically redundant, or whether expensive work is being refreshed more often than its inputs change.

\introhead{Explicit pipeline structure}
At the same time, modern analytics pipelines increasingly make dependencies explicit. Analytics engineers now write and maintain transformation programs in which one SQL-defined asset consumes another, producing a source-level graph of recurring computation.\footnote{Examples include dbt~\cite{dbtLineage}, SQLMesh~\cite{sqlmeshOverview}, Dagster~\cite{dagsterAssets}, Airflow~\cite{airflowDags}, Prefect~\cite{prefectTasks}, Argo Workflows~\cite{argoDag}, Databricks Workflows~\cite{databricksJobs}, and medallion lakehouse pipelines~\cite{databricksMedallion}.} We view these as instances of a \emph{SQL pipeline DAG}: a recurring directed acyclic graph whose nodes are SQL transformations or materialized relational assets, and whose edges are data dependencies. Figure~\ref{fig:intro-example} shows the kind of structure such a DAG exposes: dependencies, intermediate boundaries, refresh cadences, and downstream consumers are visible at the source level rather than hidden inside a single query.

\introhead{Limitation of existing approaches}
Existing database techniques use only fragments of this information. Single-query rewriting optimizes one statement at a time. Multi-query optimization shares work across a workload, but typically treats the workload as a flat set of queries and relies on syntactic overlap~\cite{sellis1988multiple}. Materialized-view selection chooses useful persisted expressions, but does not generally rewrite the maintained pipeline around dependency structure, intermediate contracts, or refresh schedules~\cite{agrawal2000automated}. Workflow schedulers know dependencies, but usually optimize execution order, invalidation, or retry policy rather than semantic SQL. This comparison belongs early because it identifies the missing optimization object: the maintained SQL pipeline program itself.

\introhead{Key insight}
The key observation behind \tool is that dbt-style SQL pipeline DAGs expose six optimization opportunities that are unavailable to a single-query rewriter, a flat multi-query optimizer, or a materialized-view advisor. \textbf{(1) Cross-boundary semantics:} the optimizer can reason about the meaning of a node by reading related upstream, sibling, and downstream SQL definitions. \textbf{(2) Intermediate contract freedom:} internal nodes can be narrowed, split, merged, or removed as long as externally consumed outputs are preserved. \textbf{(3) Non-local semantic reuse:} logically equivalent work may appear in different branches with different syntax, names, predicates, or aggregation boundaries. \textbf{(4) Rewrite-materialization coupling:} whether a rewrite helps depends on table/view/incremental materialization choices, and those choices depend on the rewritten graph. \textbf{(5) Freshness-aware recomputation:} in cloud warehouses, cost and latency depend on how often sources change, how often outputs are consumed, and which nodes lie on critical refresh paths. \textbf{(6) Global rewrite composition:} DAG-level rewrites can overlap or interact, so locally beneficial changes must be selected as a compatible set.

\introhead{System overview}
\tool exploits these opportunities with a dependency-aware rewriting pipeline. It identifies promising regions of the SQL pipeline DAG, asks an LLM to propose graph-level refactorings, filters unsafe or counterproductive proposals, verifies adopted rewrites with warehouse-backed diagnostics, evaluates each candidate under an optimized materialization configuration, and selects a non-conflicting set of rewrites globally. The result is a rewritten pipeline that remains executable by the same warehouse and orchestration framework, but exposes less redundant work and better aligns computation with materialization and refresh behavior.

\introhead{Contributions}
This paper makes the following contributions:
\begin{itemize}[leftmargin=*, topsep=2pt, itemsep=1pt]
    \item We introduce, to the best of our knowledge, the first holistic source-to-source query rewriting framework for dbt-style SQL pipeline DAGs: recurring SQL transformation pipelines with explicit dependencies, intermediate node contracts, materialization choices, and refresh constraints.
    \item We identify six optimization opportunities enabled by explicit pipeline dependencies: cross-boundary semantics, intermediate contract freedom, non-local semantic reuse, rewrite-materialization coupling, freshness-aware recomputation, and global rewrite composition.
    \item We present \tool, which combines structural graph analysis, LLM-guided refactoring, empirical equivalence checking, learned cost modeling, materialization tuning, frequency-aware scheduling, and global candidate selection.
    \item Our evaluation will show that \tool reduces end-to-end warehouse cost by \textbf{XX\%} over the original pipeline, by \textbf{YY\%} over materialization-only tuning, and by \textbf{ZZ\%} over single-query rewriting baselines, while improving sink refresh latency by \textbf{LL\%}. These placeholders will be replaced with final measurements in Section~\ref{sec:eval}.
\end{itemize}
